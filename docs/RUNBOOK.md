# KAIROS Production Runbook 🚀

This document serves as the ultimate operational guide for deploying, managing, and troubleshooting the KAIROS AI-Powered DevOps Incident Intelligence Platform in a production Kubernetes environment.

---

## 🏗️ 1. Architecture Overview

KAIROS is a distributed system comprised of the following core components:
- **Frontend**: React (Vite, TailwindCSS, Framer Motion)
- **Backend API**: FastAPI (Python 3.12, Clean Architecture)
- **Background Workers**: Celery + Redis
- **Primary Datastore**: PostgreSQL 16 (StatefulSet)
- **Cache / Message Broker**: Redis 7
- **Ingress Controller**: NGINX Ingress
- **Observability Stack**: OpenTelemetry + Prometheus + Jaeger (Simulated/Ready)

---

## 🚢 2. Kubernetes Deployment

The platform is deployed via Kustomize using three environments: `base`, `local`, and `production`.

**To deploy locally:**
```bash
make deploy-local
```
*This spins up a complete k3d cluster with all services, applies the Kustomize manifests, and sets up NGINX Ingress.*

**To inspect the cluster:**
```bash
kubectl get pods -n kairos
kubectl get svc -n kairos
kubectl get ingress -n kairos
```

---

## 📈 3. Autoscaling (HPA)

The system is configured with Horizontal Pod Autoscaling (HPA) targeting a 70% CPU utilization threshold. 

**To view active scaling metrics:**
```bash
kubectl get hpa -n kairos -w
```

**To trigger a load test and force scaling:**
```bash
python backend/scripts/load_test.py
```
*This will fire 5,000 concurrent requests at the backend, causing the HPA to automatically provision more replica pods.*

## 🛡️ 4. Security & Rate Limiting

The API is hardened against attacks:
- **CORS**: Locked down to explicit frontend domains (`app.kairos.local`).
- **OWASP Headers**: `Content-Security-Policy`, `HSTS`, `X-Frame-Options` strictly enforced.
- **Rate Limiting**: Backed by Redis via `fastapi-limiter`. 
  - `POST /api/v1/auth/login`: 10 requests / min.
  - `POST /api/v1/ai/chat`: 20 requests / min.

## 🛟 5. Disaster Recovery

KAIROS comes with automated scripts for PostgreSQL disaster recovery.

**To Backup the Database:**
```bash
./k8s/scripts/backup_postgres.sh
```
*This executes a `pg_dumpall` inside the active Kubernetes Postgres pod and saves a `.sql` file to the host machine's `./backups` directory.*

**To Restore the Database:**
```bash
./k8s/scripts/restore_postgres.sh ./backups/kairos_pg_dump_<timestamp>.sql
```
*⚠️ Warning: This will overwrite existing data.*

## 🕵️ 6. Troubleshooting & Triage

**Issue: Pods are stuck in `Pending` state.**
* **Cause**: Usually lack of CPU/Memory resources on the host machine.
* **Fix**: Check `kubectl describe pod <pod-name> -n kairos` to confirm. Increase Docker/WSL memory limits.

**Issue: `502 Bad Gateway` from API.**
* **Cause**: The backend pod is crashing or the readiness probe is failing.
* **Fix**: Check backend logs: `kubectl logs -f -l app=backend -n kairos`.

**Issue: Celery Workers are not processing tasks.**
* **Cause**: Redis connection failure or worker crash.
* **Fix**: Restart the worker deployment: `kubectl rollout restart deployment worker -n kairos`.
